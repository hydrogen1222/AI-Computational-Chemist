# 课题说明的写法

课题说明（文件 `00_project_overview.md`）是一个计算课题的**人类版正本**。当前进度另写在根目录的 `01_project_status.md`；执行用的参数和步骤放在 `docs/execution_sheet.md`，详细台账放在 `docs/calculation_ledger.md`。完整文件位置见 `AGENTS.md` 的 *Project document layout*。课题说明要让课题的主人随时能回答三件事：这个课题想回答什么，每一步为什么这样算，结果出来以后该怎么读。

## 谁用这份 skill

| 角色 | 怎么用 |
|---|---|
| SI（科学决策角色） | 始终聚焦科学问题：确认任务定义、写和修订科学路线图、解释结果、决定是否需要改变科学路线。SI 不以“模型必须最强”为定义，也不沉入提交、监控和报错细节 |
| major（准备与编译工作流的 agent） | 把 SI 批准的科学路线图翻译成人能看懂的 work package，再准备完整计算目录、检查和交接。把 SI 回复替换进课题说明并记录变更，自己不改 SI 的科学内容 |
| vice（执行和监控的 agent） | 执行 major 已经准备好的工作，监控任务、按允许范围恢复错误、记录原始运行事实；不自行改变科学路线 |

用户用 `??` 标记读不懂的句子，处理办法见 `AGENTS.md` 里的 *Writing for the user*，这里不重复。

## 读者是谁

- 懂 DFT 和 VASP 的凝聚态物理博士生，第一次看这个课题。
- 结构优化、高精度单点计算这类常规操作不用解释。
- 读者会查资料：教科书级的概念给出处或关键词就够，不展开。
- 读者用中文阅读。INCAR 参数名、文件名、软件名保持英文原样。

## 固定结构

课题说明只有五节，编号固定。修订时按编号替换，所以编号永远不变。各节内部可以有 3.1、3.2 这样的小节，小节编号一旦给出也不再改。

1. **一句话问题**：这个课题到底想回答什么。先用一句话说完，再用一两段说清楚这句话里每个词指的是什么。
2. **为什么值得做**：和已有文献的关系，前人做到了哪里，还缺什么。引用写出作者、年份和期刊。
3. **计算路线图**：一步一个小节。每个小节说清楚三件事：这一步回答哪个子问题，为什么排在这个位置，它依赖前面哪一步的结果。
4. **结果怎么读**：和第 3 节一一对应。每一步都提前写好"如果算出来是这样，说明什么；如果是那样，说明什么"，并给出判断的大致数值范围。写成叙述，不写成问答。
5. **不做什么**：明确排除的方向，每条附一句原因。头脑风暴中被淘汰的点子也写在这里，这样它们不会被悄悄加回来。

## 原始计算和结果怎么写给人看

AICC 的用户文档先服务于理解，再服务于展示。原始计算、阶段结果和台账说明
使用最简单的准确表述。汇报或论文需要更正式的语言时再单独润色。

- 软件内部状态尽量翻译成科研动作，例如写“这个结构检查通过后再提交计算”，
  不写“通过 gate 后 release downstream task”。
- 除非正在讨论软件架构，用户文档避免 gate、port、watchdog、DAG、artifact、
  pipeline stage 一类计算机术语和比喻。
- 一个 work package 只用一句话说明一个科学目的。多个结构、多个温度或多个
  构型属于同一个问题时，可以作为同一个 work package 的计算对象，不为了机器
  执行方便拆成很多用户可见的“步骤”。
- “做完以后我们会知道什么”必须写成直接的科学结论类型，例如“知道哪个 Na
  空位位置更稳定”，不要写成抽象的“为后续决策提供依据”。

## 课题总览和当前进度分开写

`00_project_overview.md` 专注科学问题、已有研究、当前批准的计算路线和
SI 已确认的结果解释；不粘贴 Slurm 队列、每天的进度数字和失败重试细节。

`01_project_status.md` 专注**现在**：当前研究阶段、每个 Work 已完成多少，
得到哪些可以直接陈述的结果及其来源，哪些仍有疑问，当前机器在算什么，
以及一条具体的「接下来」。正常情况下控制在一到两屏，不把旧版本依次追加。

详细历史写进 `docs/calculation_ledger.md` 和 `docs/change_log.md`。当 SI
修订路线并获得需要的用户批准后，major 替换总览的相应段落，刷新当前进度，
保留旧计算和历史决定。已被新方案取代的有效计算应标记为「已被取代」，
不应写成「失败」。一个项目只有一个总 Workflow，下面可以有多个 Stage、
Work package 和 calculation。

## 写法规则

1. **只回头引用，不提前剧透。** 每个概念第一次被用到之前，必须已经讲过。禁止"详见第 5 节""后面会讲到"这类往后指的说法。某个概念非得先用，就在用到它的地方当场讲清楚。
2. **每节开头一句话**，说明这一节要解决什么，和上一节怎么接上。
3. **讲故事，不列提纲。** 主体是成段的叙述，前一段的结论引出后一段的问题。只有真正并列的几项（比如要算的几种结构）才用列表，列表最多两层。
4. **预判读者会卡在哪。** 在读者可能想问"为什么不用另一种做法"的地方，用一两句话主动解释，融进叙述里。
5. **新词第一次出现时用一句话解释**，之后一直用同一个叫法，不换同义词。
6. **详略得当。** 主线写详细，旁支一句话带过并给出处。
7. **数字带单位和出处。** 每个数值写清单位。来自文献的写出处，来自本课题计算的写计算目录。

## 绝对禁止

- **自创代号。** 工作流自己发明的字母编号一律不出现，例如 P0、P1、C2、I3、Gate A、Batch 3、S1。一个状态或一个计算用它的完整描述来称呼，比如"第一根 P-S 键断开之后的结构"。
- **术语表之外的缩写。** 领域通用词可以直接用（DFT、PBE、HSE06、NEB、AIMD、INCAR 参数名）。其他缩写第一次出现必须展开，并且先确认术语表里有它。
- **问答体和提纲体。** 不写"Q：…… A：……"，不用一个点接一个点却没有因果的罗列。
- **只下结论不给理由。** 不写"显然""众所周知"来代替理由。

## 术语表

课题开头和课题说明一起建一份术语表，文件名固定为 `docs/glossary.md`，markdown 表格，四列：

| 词 | 一句话意思 | 第一次出现在课题说明哪一节 | 哪天加的 |
|---|---|---|---|

只有 SI 能往术语表里加词，加词时在回复里明确写出来，由 major 记进变更日志。major 和 vice 遇到表里没有的东西，用完整的话描述，不自己造词，也不为此打断用户。

## 修订时的输出格式

课题进行中修改方案时，**只输出改动的那一节或小节**，不重写全文。格式固定为：

```
替换第 3.2 节
（新的 3.2 节全文）

变更理由：一两句话，说明为什么改。
```

如果改动涉及第 5 节"不做什么"（比如把以前排除的方向加回来），必须单独点明，并说明理由。

## 对比例子

不好的写法（提前剧透、代号、提纲体）：

> P1 阶段：构建 C0–C4（详见 3.4），I-states 用于 NEB（见 P2）。Gate E 通过后提交。

好的写法：

> 有了体相的参考能量，下一步看局部结构怎样一步步被还原。我们从一个 64 个原子的 Na3PS4 超胞出发，选中靠近中心的一个 PS4 单元，每次往它旁边放两个钠原子，看一根 P-S 键会不会断开。之所以每次放两个钠，是因为断开一根 P-S 键在形式上需要两个电子。为了区分"放进钠要花多少能量"和"放进钠以后断键是否有利"，每一步都算两个结构：钠已经放进来但键还连着的结构，以及键断开之后的结构。这两个结构原子数相同，所以后面也可以直接用 NEB 计算它们之间的势垒。

## 一组 Work 结束后

每个 Work package 完成后，默认停止启动下一组 Work，让用户先看一页以内的结果
摘要。major 在 `01_project_status.md` 写明已完成的计算、直接结果、来源目录、
仍待判断的地方，以及当前机器或手动申请的 allocation 状态。下一组的输入可以准备，
但是用户还没有明确说继续时不能提交。已经在运行的本组计算照常完成，也不允许
agent 取消用户的 `salloc`。

根目录保留 `archive/`，容纳用户明确决定淘汰的整组计算与旧文件。
要保留原始证据和淘汰理由，台账中能追踪迁移前后的路径。待审结果先放在正常
计算目录，不能擅自归档；被弃用也不等于算错。现行计算中的技术性失败尝试
仍留在各计算目录内部的 `archive/`。

## 每轮回复的结尾

SI、major 和 vice 给用户的每一轮回复都以一条很短的 `接下来：` 收尾。
这句话写清谁来做、做什么；角色交接时还要写清要交哪些文件或计算目录。
它只描述眼前下一步，不提前罗列后面几轮工作。

示例：

> 接下来：把已经确认的第 3.2 节路线交给 major；major 先整理对应的 work
> package，暂时不要提交计算。

> 接下来：把 `calculations/011_...` 到 `014_...` 和
> `docs/execution_sheet.md` 交给 vice；vice 只负责提交、监控和记录运行结果。

不要用“如果你愿意我可以继续”“后续再看”这类没有动作的信息结束。

## 写完自检

交付之前逐条检查：

- [ ] 没有任何一句话用到后文才讲的概念
- [ ] 没有自创代号，也没有术语表之外的缩写
- [ ] 第 3 节和第 4 节的小节一一对应
- [ ] 每一节开头有一句话说明它要解决什么
- [ ] 没有写成问答或提纲的段落
- [ ] 每个数字都带了单位和出处
